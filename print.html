Bellek: free vs Drop

C modeli

Dinamik bellek açık sözleşmedir. malloc/free çiftini siz kurarsınız; unutmak sızıntı, erken/çift free UB.

char *buf = malloc(64);
if (!buf) return -1;
/* ... */
free(buf);
buf = NULL;

Birden fazla işaretçi aynı bloğu gösteriyorsa “sahip kim?” dokümantasyondadır — derleyici bilmez.

Rust modeli

Sahiplik bitince Drop çalışır. Sızıntı için bilinçli mem::forget / Box::leak gerekir.

#![allow(unused)]
fn main() {
let mut buf = vec![0u8; 64];
/* ... */
// drop otomatik
}

Null vs Option, errno vs Result

Null

C’de NULL her yerde; unutulmuş kontrol → UB.

size_t n = strlen(p); /* p NULL ise UB */

Rust’ta null referans yoktur. Yokluk Option:

#![allow(unused)]
fn main() {
fn uzunluk(p: Option<&str>) -> usize {
    p.map(|s| s.len()).unwrap_or(0)
}
}

FFI’da nullable pointer → Option<NonNull<T>> veya *mut T + dokümantasyon.

Hatalar

CRust
int rc / errnoResult<T, E>
out-parametre T *outResult<T, E> veya (T, Warn)
“0 başarı” karışık APItek politika seçin
int parse(const char *s, int *out);

#![allow(unused)]
fn main() {
fn parse(s: &str) -> Result<i32, ParseError> { /* ... */ }
}

unwrap gerçeği

unwrap/expect C’deki “assert non-null sonra kullan”a benzer — prototip OK, kütüphane sınırında ? tercih.

Derleme birimi vs crate

C

  • .c → çeviri birimi; başlıklar metin include
  • Bağlayıcı sembolleri birleştirir
  • static iç bağlama; inline kuralları incelikli
  • Build: Make/CMake + pkg-config

Rust

  • Crate = derleme birimi + paket sınırı
  • Modüller dilde; pub görünürlük
  • Cargo bağımlılık grafiği + semver
  • Features ile koşullu derleme

Sonuçlar

  1. C’de “başlıkta tanım” tuzağı; Rust’ta monomorphization / inline farklı
  2. Versiyonlama: soname vs semver
  3. Karışık projede iki graphe (CMake + Cargo) yönetilir

UB kültürü vs safe invariants

C gerçeği

Birçok hata sınıfı UBdır ve “şimdilik çalışıyor” görünebilir. Optimizasyon, farklı derleyici veya sanitizer altında patlar. Disiplin + araçlar şarttır.

Safe Rust gerçeği

Derleyici/borrow checker invariants’ı korur. Data race, UAF, double-free safe kodda yok sayılır. UB kapısı: unsafe ve FFI.

Geçişte zihinsel tuzaklar

  1. C alışkanlığıyla raw pointer’ı her yere yaymak
  2. unsafe ile “hızlıca” borrow checker’ı susturmak
  3. C API’nin null/alias sözleşmesini Rust tipine yansıtmamak

Strateji

Önce idiomatik safe Rust; FFI sınırını ince tutun; her unsafe için SAFETY yorumu ve test (Miri).

Struct layout ve repr(C)

Sorun

Rust varsayılan layout’u optimize edebilir (alan sırası değişebilir). C ABI ile paylaşımda:

#![allow(unused)]
fn main() {
#[repr(C)]
pub struct Point {
    pub x: f64,
    pub y: f64,
}
}

Kontrol listesi

  1. #[repr(C)] (veya u32 enum)
  2. Padding/alignment her iki tarafta aynı
  3. #[test] fn layout() { assert_eq!(size_of::<Point>(), 16); }
  4. Bitfield / packed → mümkünse kaçının; memcpy alan alan

Opaque pointer kalıbı

C’ye yalnızca struct Foo *; gösterin; layout’u saklayın.

Kaynaklar

  • Nomicon FFI

FFI kontrol listesi

  • extern "C" / #[no_mangle]
  • #[repr(C)] layout testi
  • ownership (kim free eder?)
  • nullability
  • panic politikası
  • thread safety (Send/Sync)

Generics vs _Generic

C tarafı

C’de aşırı yükleme yoktur. Yaklaşımlar:

  1. Makrolar — metin; yan etki ve tür güvenliği zayıf
  2. _Generic (C11) — derleme zamanı tür seçimi
  3. void * + boyut — tip silme; hata çalışma zamanına kaçar
  4. Kod üretimi (X-macro) — tekrarlayan fonksiyonlar
#define MAX(a,b) _Generic((a), \
    int: max_int, \
    double: max_double \
)(a,b)

Sınır: açık tür listesi; trait bound yok; coherence yok.

Rust tarafı

#![allow(unused)]
fn main() {
fn max<T: PartialOrd>(a: T, b: T) -> T {
    if a > b { a } else { b }
}
}

Monomorphization veya dyn. Orphan rule, associated types, GAT — C’de karşılığı zayıf olan kavramlar.

Geçiş stratejisi

C makro/_Generic ormanını birebir çevirmeyin. Önce:

  1. Ortak davranışı trait olarak adlandırın
  2. Somut türleri impl edin
  3. Gerekirse dyn ile heterojen koleksiyon

Alıştırmalar

  1. C _Generic max’ını Rust generics’e çevirin.
  2. Aynı API’yi dyn ile yazıp farkı ölçün.

Kaynaklar

  • Book ch.10
  • cppreference _Generic

c.fetch_add(1, Ordering::SeqCst);

goto cleanup → Drop

C kalıbı

int run(void) {
    A *a = NULL; B *b = NULL; int rc = -1;
    a = a_new(); if (!a) goto done;
    b = b_new(); if (!b) goto done;
    rc = work(a, b);
done:
    b_free(b);
    a_free(a);
    return rc;
}

Tek çıkış noktası kaynak sızıntısını azaltır; ama goto disiplini gerekir.

Rust karşılığı

#![allow(unused)]
fn main() {
fn run() -> Result<(), Error> {
    let a = A::new()?;
    let b = B::new()?;
    work(&a, &b)?;
    Ok(())
} // a, b drop — sıra ters
}

Erken ? dönüşlerinde bile Drop çalışır. Bu, C goto cleanup’ın dil düzeyinde yerleşmiş hâlidir.

İnce noktalar

  • Drop sırasında panic → abort riski; Drop içinde paniklemeyin
  • Kısmi init: alanları Option yapın veya builder kullanın
  • FFI’dan alınan kaynak: Drop’ta extern free çağırın

Alıştırmalar

  1. Üç kaynaklı C cleanup’ı Rust’a çevirin.
  2. Bilerek Drop içinde panic deneyip ne olduğunu görün (küçük örnek).

Kaynaklar

  • Book ownership / Drop
  • C cleanup stili (Linux kernel tartışmaları)

Vaka: dinamik dizi (realloc vs Vec)

C

int *data = NULL; size_t len = 0, cap = 0;
int push(int v) {
    if (len == cap) {
        size_t n = cap ? cap * 2 : 4;
        int *p = realloc(data, n * sizeof *p);
        if (!p) return -1;
        data = p; cap = n;
    }
    data[len++] = v; return 0;
}

Rust

#![allow(unused)]
fn main() {
let mut data = Vec::new();
data.push(v);
}

Hash map FFI sarmalayıcı

C API: map_create / map_insert / map_get / map_free. İçeride Rust HashMap; dışarıda opaque pointer.

#![allow(unused)]
fn main() {
pub struct Map(std::collections::HashMap<u32, u32>);

#[no_mangle]
pub extern "C" fn map_create() -> *mut Map {
    Box::into_raw(Box::new(Map(Default::default())))
}

#[no_mangle]
pub unsafe extern "C" fn map_insert(p: *mut Map, k: u32, v: u32) -> i32 {
    if p.is_null() { return -1; }
    (*p).0.insert(k, v);
    0
}

#[no_mangle]
pub unsafe extern "C" fn map_free(p: *mut Map) {
    if !p.is_null() { drop(Box::from_raw(p)); }
}
}

SAFETY: p ya null ya da map_create ürünü; double-free yok.

C

#include <stdatomic.h>
atomic_long c = 0;
atomic_fetch_add_explicit(&c, 1, memory_order_relaxed);

Rust

#![allow(unused)]
fn main() {
use std::sync::atomic::{AtomicI64, Ordering};
static C: AtomicI64 = AtomicI64::new(0);
C.fetch_add(1, Ordering::Relaxed);
}

Anlamlar benzer; Rust’ta AtomicI64: Sync paylaşımı türe gömülüdür. Yanlış Ordering her iki dilde de ince bug üretir.
